# #17 성능 개선과 운영 검증

## 바뀐 경로

- 일반전 제출: 인증된 회원/게스트·현재 문제·기존 시도를 인덱스 조회 한 번으로 읽는다. 최초 시도는 빈 플레이 생성 없이 조건부 UPSERT 한 번으로 저장한다. 현재 판·계정 우선순위·강퇴·관전·이전 시도·DB 실행 시점의 제한시간을 검사한다. 아이템/연습/기존 판은 기존 권한 경로를 유지한다.
- 진행판: GET 중복 인증 제거, 서로 독립인 데이터는 먼저 읽고 필요한 시점에 합친다. 칭호/그림 목록·채팅과 참가자 조회는 D1 배치로 왕복을 줄인다. 판정 전의 정답이나 다른 참가자의 입력 단어는 공개하지 않는다.
- 안전 경계: IP/주체 도배 제한은 한 번의 원자적 SQL로 함께 처리한다. 매 쓰기마다 전체 만료 카운터를 정리하던 작업은 이미 배포된 제한 정리 Cron에 맡긴다. 본인 제출 확인 응답은 사회적 정보가 없는 정확한 필드 목록일 때만 차단 목록 재조회를 생략한다. 채팅/힌트/다른 필드가 추가되면 기존 차단 필터를 거친다.
- 대기실·친구·프로필·상점: 독립 조회를 병렬 처리한다. 개인 도전은 기존 기록 조회 때 무조건 INSERT하지 않는다.
- 입력: 공개 표제어 사전은 브라우저에서 한 번 내려받아 공유한다. 발견한 단어만 빠르게 긍정 표시하고, 사전 미포함/다운로드 실패는 서버 검사로 돌린다. 실제 제출은 항상 서버 사전 검증을 거친다. 정답 풀을 클라이언트에 추가하지 않는다.
- Worker Smart Placement 설정을 추가한다. 배치/인덱스와 별개인 실행 위치 최적화이며 실제 배치 결정이나 속도 효과가 즉시 보장되지는 않는다.

개인 응답 캐시·Redis·WebSocket은 추가하지 않았다. 이번에 확인된 병목인 DB 왕복과 전체 스캔부터 줄였다. 게임 상태/권한/보상을 오래 캐시해서 빨라 보이게 만들지 않는다. 이후 안정적 대규모 동접이 필요하면 방 단위 변경 알림과 읽기 부하 분산을 별도 측정한다.

## 평소 한 사람이 사용하는 경로

입장 응답에 권한 검사를 거친 게임판을 함께 보낸다. 새 게스트는 서버가 발급한 쿠키로 본인 스냅샷을 읽고, 기존 Google 계정 우선순위·비밀번호·관전 제한은 유지한다. 입장은 성공했는데 스냅샷만 실패하면 roomId만 반환해 클라이언트가 읽기만 재시도한다. 방 생성 쓰기를 자동 재전송하지 않는다. 기존 이름/캐릭터가 같으면 UPDATE를 생략한다.

대기실 방 목록/프리뷰 조회와 친구·채팅·공지를 동시에 시작한다. 나가기는 기존처럼 네트워크 완료를 기다리지 않고 즉시 대기실로 전환한다. 사전은 문제에 들어올 때 미리 준비하고, 메모리에서 확인되는 표제어는 180ms 대기나 서버 호출 없이 긍정 표시한다. 그림 힌트 POST의 중복 권한 조회를 제거하고, 이미 열람한 힌트는 다시 쓰지 않는다. 열린 뒤의 갱신은 GET으로 읽는다.

같은 보호 QA 서버에서 한 플레이어가 순서대로 각 8회 사용한 HTTP 중앙값/p95다. 아래 '전'도 이 PR의 앞선 서버 개선본이며, 마지막 입장·대기실·힌트 보강 직전과 직후를 비교했다. 스토리/그림이 존재하도록 만든 합성 QA 데이터만 사용했다. 실제 기기의 화면 그리기 시간이나 전체 이용자의 속도 보장이 아니다.

| 동작 | 중앙값 전→후 | p95 전→후 |
|---|---|---|
|입장부터 본인 게임판 수신|1281→592ms|1480→717ms|
|대기실 조회|579→350ms|997→660ms|
|그림 힌트 열기|987→390ms|1070→470ms|

서버 단어 검사는 533→374ms(중앙값)였다. 서버 검사 자체의 코드 변경만으로 이 차이가 났다고 단정하지 않는다. 브라우저에서 공개 표제어를 이미 읽었으면 이 서버 왕복 자체를 생략한다. 새 표제어/미확인 단어는 서버 검사로 확인하며 실제 제출 검증은 생략하지 않는다.

## 같은 격리 서버의 HTTP 비교

운영 DB와 Google 키가 없는 `jamopop-qa-p0`에서 합성 참가자를 최대 10명씩 여러 방에 배치했다. 외부 왕복을 포함한 요청 시간이다. 기기/네트워크·콜드 상태·실행 위치가 일정하지 않은 일회성 비교이며 인프라의 SLA나 모든 이용자의 개선률이 아니다.

| 동시 요청 | 첫 진행판 p95 전→후 | 제출 p95 전→후 | 제출 후 재조회 p95 전→후 |
|---|---|---|---|
|10|1592→914ms|1357→512ms|1493→584ms|
|50|3127→1869ms|1993→695ms|2788→1431ms|
|100|이전 실행 미완료 / 최종 3121ms|최종 1057ms|최종 2640ms|

이전 100명 실행은 재전송 예상 상태 검사를 통과하지 못했다. 그때 상태 분포를 도구가 보관하지 않아 503/429/다른 원인 중 하나로 단정하지 않는다. 도구에 상태별 집계를 추가했고 최종 10/50/100 시험은 모두 제출 200, 재전송 409, 재조회 정확히 한 줄 보존을 통과했다. 예전 P0에서 관측한 503의 원인을 해결했다고 주장하지 않는다.

[이전 측정](qa/perf17-baseline-bursts.json) · [최종 측정](qa/perf17-final-bursts.json).

## 여러 화면을 함께 쓰는 시험

가상 회원 15명·게스트 15명이 3개 방에서 진행판을 3초 간격으로 읽으며 대기실·채팅 조회·상점·프로필·개인 도전을 함께 사용했다. Google 세션 레코드는 QA에만 만든 합성 데이터다. 실제 Google OAuth 로그인 인수와 다르다.

123초/40주기 결과: 진행판 1200회 모두 정상이고 정확히 한 시도 유지, 중복 제출 120회 모두 409, 오류 0. p95는 진행판 1240ms·대기실 1240ms·프로필 826ms·상점 691ms·개인 도전 717ms·대기실 채팅 395ms였다. [집계](qa/perf17-mixed-2min.json).

최초 6분 시험은 진행판 3540회 중 503 한 건이 있었다. 구조화 로그에서 GET /api/game의 session 0ms·safety 18ms, SQL/왕복 1회, storageErrors=1을 확인했다. 단일 안전 제한 SELECT가 실패한 위치까지 확인했으며 제공자 내부 원인은 단정하지 않는다. [재시도 전 집계](qa/perf17-mixed-before-retry.json).

단일 SELECT의 first/all/raw만 25–49ms·50–74ms 대기 후 최대 두 번 재시도하도록 보강했다. INSERT/UPDATE/RETURNING·run·복합 문장·batch는 재시도하지 않는다. 지속 실패는 권한을 허용하지 않고 기존 오류 경계로 반환한다. 재시도 횟수와 저장 바인딩 호출을 별도로 집계한다. 단위 시험은 최초 실패 후 복구·지속 실패·쓰기 미재전송을 확인한다.

보강 후 363초/118주기 재시험은 진행판 3540회 모두 200, 중복 제출 360회 모두 409, 기록 불일치/오류 0이었다. 제한시간 후 QA DB의 해당 30개 플레이는 모두 lost이고 시도 수가 정확히 1개씩 남았다. [재시험 집계](qa/perf17-mixed-after-retry.json). 이 시험만으로 몇 시간 단위의 100명 지속 접속·모든 네트워크·운영 비용 상한을 보장하지 않는다.

## 방 수가 늘어난 대기실 경계

추가 90초 혼합 회귀에서 합성 방이 102개가 되자 대기실 60회가 모두 503이었다. 다른 진행판 900회/제출 30회는 정상이었고, 로그는 handler의 저장 조회 실패를 가리켰다. 기존 프리뷰 조회가 방 100개 ID와 시각을 각각 bind하여 101개를 전달하는 구조였다. [D1의 쿼리당 한도는 100개](https://developers.cloudflare.com/d1/platform/limits/)다. 방 ID 배열을 JSON 하나로 전달하여 시각과 합쳐 2개만 bind하도록 수정했다. SQLite 회귀도 100개를 넘는 bind를 거부하게 만들고 101개 추가 방에서 대기실 200·100개 표시·hasMore를 검사한다. [발견 당시 집계](qa/perf17-mixed-lobby-boundary-before.json). 수정 후 방 100개 초과 상태와 30명 배경 시험이 겹치는 동안 별도 8회 입장·대기실·사전·힌트 요청도 모두 200이었다. 이때의 시간은 단독 사용 표와 조건이 달라 개선률로 합산하지 않는다. [추가 확인](qa/perf17-single-during-mixed.json).

수정 후 92초 혼합 시험은 대기실 60회/진행판 900회/제출 30회가 모두 200이고 입력 한 줄 보존을 통과했다. 중복 제출은 89회 409·1회 503이었다. 이 한 건의 원인은 해당 시점 로그가 없어 단정하지 않으며, 최초 쓰기를 자동 재전송하여 덮어쓰지 않았다. 재시험 성공만으로 제공자 일시 오류 전체가 해결됐다고 보지 않는다. [수정 후 집계](qa/perf17-mixed-lobby-boundary-after.json).

같은 코드로 로그를 수집하며 61초 재확인한 결과는 대기실 40회·진행판 600회·제출 30회 200, 중복 60회 409, 오류/입력 불일치 0이었다. 수집한 구조화 API 표본 549개에서도 5xx가 없었다. 이는 직전 일시 오류의 원인 규명이나 장기 무장애 보장은 아니다. [최종 재확인](qa/perf17-mixed-final-recheck.json).

전체 자동 검사 114개, 형식·공개 자산·타입·빌드가 통과했다.

## 인덱스·기록 보존

`0031_request_lookup_indexes.sql`은 members의 계정/게스트 조회와 plays의 참가자 전적 조회 인덱스 세 개만 추가한다. [실행 계획](qa/perf17-index-plans.json)에서 SCAN members/plays가 SEARCH ... USING INDEX로 바뀐 것을 확인했다.

운영 적용 전 비공개 백업 → 인덱스 적용 → sqlite_master 세 인덱스 확인 → 배포 기준 해시 갱신 순서로 준비했다. 전후 백업의 원래 53개 사용자 테이블 전체 내용·건수는 동일했다. 실제 계정·전적·재화·스킨·가구 삭제/익명화는 실행하지 않았다. 코드 롤백 시 인덱스는 그대로 두어도 이전 코드와 호환된다.

## 재검증

- `npm run ci`: 입력·역할·동시 첫 제출·마감 경계·차단·구매·보상·보존을 포함한다.
- `scripts/load-smoke.mjs`: 10/50/100 합성 HTTP, 운영 주소 거부.
- `scripts/service-load.mjs prepare /tmp/fixtures.json /tmp/seed.sql 30`: 가상 세션/프로필 SQL 생성. **이 SQL은 운영에 적용하지 않는다.** 토큰 파일은 비공개로 보관한다.
- 별도 QA D1에만 seed 적용 후 `JAMOPOP_QA_TOKEN=... node scripts/service-load.mjs run /tmp/fixtures.json /tmp/report.json 360`. 셸 기록에 실제 키를 직접 적지 않는다. 고정 보호 QA origin + qa=true 확인을 통과해야 실행된다.
- `scripts/interaction-smoke.mjs prepare fixtures.json context.json seed.sql`: 기존 합성 세션 두 명으로 QA 방/본인 상태를 준비하고 QA 전용 힌트 SQL을 출력한다. seed는 반드시 별도 QA DB에만 적용한다. `before/after fixtures.json context.json report.json`은 고정 보호 QA 주소에서 각 동작을 8회 순차 비교한다. 비공개 파일의 토큰/식별자는 공개하지 않는다.
- 브라우저: 등록 단어 입력 시 사전 확인 POST 증가 없음, Enter 제출 후 정확히 한 줄·자판 색 반영, 미등록 단어는 서버 검사·초안 유지 확인.
- API 구조화 로그는 고정 route·단계 소요 시간·SQL 호출 수·저장 바인딩 호출 수·확인 가능한 읽기/쓰기·스토리지 실패 횟수만 기록한다. DB 배치 실패도 집계하며 SQL/요청/오류 원문을 남기지 않는다. 운영 표본은 10%로 유지한다.

공식 근거: [D1 성능/배치](https://developers.cloudflare.com/d1/reference/faq/), [Worker Placement](https://developers.cloudflare.com/workers/configuration/placement/). D1은 단일 DB에서 쿼리를 순서대로 처리하므로 Promise.all만으로 DB 처리량이 무한히 늘어난다고 가정하지 않는다.

저장 바인딩 호출 수는 애플리케이션이 호출한 first/all/raw/run/batch를 센다. 제공자 내부 재전송이나 네트워크 패킷 수를 전수 관측한 수치는 아니다.
