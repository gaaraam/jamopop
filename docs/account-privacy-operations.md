# 계정·개인정보 운영 (#16)

## 이번 구현: 본인 계정 삭제 요청 접수

내 정보 → 계정 삭제 요청 → 문의하기의 전용 영역에서 `계정 삭제 요청`을 입력한다.
Google 세션을 검증한 Worker의 계정 식별자를 서버에서 사용한다. 닉네임·이메일·클라이언트가 보낸 owner 값으로 대상을 지정하지 않는다.

- 요청은 기존 비공개 문의함에 `계정 삭제` 유형으로 저장된다. 일반 문의 작성으로 이 유형을 만들 수 없다.
- 요청자는 자신의 문의만, 관리자는 관리자 문의함에서 요청과 계정 참조값을 확인한다.
- 진행 중 요청이 있으면 새 요청 대신 같은 접수 번호를 반환한다. SQL 단일 쓰기의 조건으로 다중 탭·동시 요청도 중복을 막는다.
- 게스트는 로그인 계정 삭제 요청을 할 수 없다. 게스트 기록은 일반 문의로 접수하고 별도로 소유권을 확인해야 한다.
- 접수·확인 중·답변 완료는 **삭제 완료가 아니다**. 이 유형은 일반 문의 종료 기능으로 닫을 수 없다. UI와 API 모두 이를 제한한다.
- 접수 시 게임·프로필·재화·스킨·가구·연결 정보는 수정하거나 삭제하지 않는다.

관리자는 계정 참조값을 기준으로 연결된 Google/Sites 프로필과 요청 범위를 확인한 뒤 답변한다. 공개 이슈나 로그에 이 참조값, 이메일, 원본 기록을 붙이지 않는다. 현재 답변은 수정 가능하며, 불변 감사 로그나 실제 삭제 실행 증빙을 대신하지 않는다.

## 실제 삭제 실행 전 필요한 후속 작업

이 PR은 #16을 닫지 않는다. 다음 작업이 남아 있다.

1. 현재 계정과 이전 프로필 연결을 포함한 데이터 소유 관계를 정리하고 삭제 대상 미리보기를 제공한다. 다른 사람의 방·공유 게임 기록은 연쇄 삭제하지 않는다.
2. 관리자 실행 확인, 대상 버전 확인, 재시도 가능한 삭제/익명화, 세션 폐기 및 실행 감사 로그를 구현한다. 테스트 계정으로 접수부터 완료까지 검증한 뒤 완료 상태를 연다.
3. 삭제 후 로그인이 불가능해지는 이용자에게 완료 결과를 전달할 방법을 정한다. 현재 문의함 조회만으로 완료 안내가 충분하다고 간주하지 않는다.
4. 채팅·그림·문의·접속 로그·백업의 실제 저장소별 보관 목적과 기간을 운영자가 확정하고 삭제 작업을 구현한다. 확정되지 않은 기간을 정책에 약속하지 않는다.
5. 친구 접속·현재 방·집 방문·차단 동작을 소스와 운영 화면에서 대조하고 개인정보처리방침에 반영한다.
6. Google OAuth 공개 상태와 요청 권한을 확인하고 이용 연령·미성년 정책 및 법률 검토를 진행한다.

## 배포와 검증

스키마 변경 없음. 기존 inquiries의 owner/category/request_id를 사용한다. 운영 DB 마이그레이션 불필요.
자동 테스트는 비로그인/타인 조회/owner 위조/교차 출처/중복 동시 접수/관리자 답변/허위 완료 차단/일반 문의 회귀를 검증한다.
롤백 시 요청 행은 보존한다. 이전 UI에는 일반 문의처럼 보이므로 구버전으로 롤백한 운영자는 계정 삭제 요청을 일반 문의의 처리 완료 상태로 변경하지 않는다.
