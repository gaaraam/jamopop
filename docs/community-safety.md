# 신고·차단과 운영 처리

관련 이슈: #15. 운영 적용 전 `0028_community_safety.sql`이 필요합니다.

## 이용자 동선

- 대기실/방/스피드전 채팅의 더보기: 신고, 대화 숨김, 사용자 차단.
- 참가자 프로필의 더보기: 닉네임 신고와 해당 사용자 숨김/차단.
- 방 참가자 패널의 방 이름 더보기: 방 이름 신고. 비밀번호 방은 참가자만 신고할 수 있습니다.
- 열린 그림 힌트의 더보기: 그림 신고/작성자 숨김·차단. 보지 않은 비공개 힌트를 신고 API로 먼저 가져올 수 없습니다.
- 문의하기 → **차단 관리 · 내 신고**: 숨김/차단 해제, 본인의 신고 상태 확인.
- 운영 → **신고함**(`/admin/reports`): 신고 당시 사본, 사유, 상태, 조치 및 이력. 문의함과 서로 연결됩니다.

신고 원문과 조치 기록은 비공개 DB에만 저장합니다. 신고 요청에 보낸 임의의 작성자·증거는 사용하지 않고, 서버가 해당 메시지/이름/그림과 열람 권한을 확인합니다. 신고자가 볼 수 있는 것은 자신의 대상 이름·사유·상태이며, 다른 사람의 신고나 관리자 메모는 공개하지 않습니다. 원래 게시물이 나중에 숨겨져도 증거 사본은 유지됩니다.

## 숨김과 차단의 차이

| 설정 | 동작 |
| --- | --- |
| 대화 숨김 | 내가 보는 상대의 대화·응원·그림을 숨김. 친구 관계와 초대는 유지 |
| 사용자 차단 | 위 내용에 더해 서로의 친구 요청·수락·초대·초대 수락·집 방문을 제한. 친구/최근 함께한 사람과 초대 알림에서도 제외 |

게임 카드, 진행 색상, 순위, 제출 기록, 이미 남긴 집 방문 인사는 삭제하지 않습니다. 같은 게임에 존재하는 것 자체를 막거나 강퇴하는 기능은 아닙니다. 친구 관계 원본도 삭제하지 않아 해제 후 다시 보입니다.

설정은 DB에 저장해 새로고침/기기 변경에도 같은 회원 계정에서 유지합니다. 기존 방 참가자의 게스트 식별값도 함께 확인합니다. 새 게스트 쿠키나 별도 계정은 동일인으로 확정할 수 없습니다. 익명 이용자의 완전한 재가입 방지를 보장하지 않습니다.

## 운영 기준

자동 판단으로 제재하지 않습니다. 관리자가 증거와 기존 조치 이력, 피해 정도를 확인한 뒤 사유를 기록합니다.

| 조치 | 사용할 상황 | 영향 |
| --- | --- | --- |
| 주의 안내 | 경미한 첫 위반 또는 규칙 안내가 필요한 경우 | 안내만 표시, 게임·채팅 가능 |
| 대화·그림 공유 제한 | 반복 도배, 모욕, 부적절한 그림 공유 | 채팅·응원·그림 업로드 제한, 게임은 계속 가능 |
| 이용 일시 제한 | 위협/개인정보 노출/반복적 심각한 피해 등 즉시 중지가 필요한 경우 | 게임·소통 API 접근 제한 |
| 제한 해제 | 오인 조치, 이의 인정, 해제 결정 | 현재 대상의 제한 해제 |

기간은 1시간/24시간/7일입니다. 상태·메모만 저장할 수도 있습니다. 사유와 기한을 대상 사용자에게 안내하고, `/support` 및 `@문의`를 통한 이의 신청은 제한 중에도 열어 둡니다. 신고 사본과 검토 메모는 일반 게시물로 전송하지 않습니다. 공개 게시물을 내릴 필요가 있으면 기존 관리자 메시지/그림 내리기를 별도로 사용합니다.

각 저장은 신고 revision을 비교하는 원자적 batch입니다. 다른 운영자가 먼저 저장했으면 409로 거절하며, 제한과 이력을 중복 적용하지 않습니다. `safety_actions.actor`에는 처리한 계정을 남깁니다. 화면에는 운영자 프로필 이름과 시각을 표시합니다. 새 조치는 기존 제한을 대체하므로 이력을 읽고 결정합니다. 해제 역시 기존 이력을 지우지 않습니다.

## 요청 제한

Cloudflare Worker에서 검증된 로그인 또는 게스트 쿠키 식별값과 IP 해시를 조합합니다. IP 원문과 쿠키 원문은 카운터에 저장하지 않습니다. 다른 회사 동료의 정상 이용을 막지 않도록 IP 한도는 개인 한도보다 넉넉하게 둡니다. 신뢰 헤더를 제거한 뒤 서버가 Google 세션에서 만든 계정 정보만 사용합니다.

| 행위 | 개인 한도 | IP 한도 |
| --- | --- | --- |
| 방 생성 | 5회/시간 | 150회/시간 |
| 채팅 | 25회/분 + 기존 1.5초 간격 | 1,000회/분 |
| 친구 요청 / 초대 보내기 | 각각 10회/분 | 각각 300회/분 |
| 문의 | 10회/시간 | 200회/시간 |
| 신고 | 5회/시간 | 100회/시간 |
| 로그인 시작 | 식별값이 있으면 10회/5분 | 100회/5분 |
| 방 입장 | 30회/분 | 600회/분 |
| 비밀번호 확인 | 기존 방별 개인 10회/분 | 추가 방별 60회/분 |
| 그림 업로드 | 10회/분 | 300회/분 |
| 기타 변경 요청 | 180회/분 | 3,000회/분 |

동시 요청에도 SQL 조건으로 제한하며 429와 `Retry-After`를 반환합니다. 고정 시간창이라 경계 직전/직후에는 두 창의 요청이 붙을 수 있습니다. 차단/숨김 설정은 200개까지입니다. 읽기 폴링은 쓰기 한도를 소모하지 않습니다. 별도의 짧은 폴링을 추가하지 않았고, 제한 안내는 최초 조회와 명시적 설정 변경 시 갱신합니다. 기존 화면의 주기 조회에서도 서버 제한은 즉시 적용됩니다.

`/api/safety`는 Worker에서 직접 처리합니다. 기존 API를 내부 함수로 호출하는 경로는 외부 Worker 경계를 다시 통과하지 않습니다. 그래서 외부 초대 수락 시 차단을 먼저 확인하고, 실제 입장 함수에서도 비밀번호를 검증합니다. 신고 처리 UI는 별도 페이지이지만 권한 검사는 Worker의 인증 결과가 기준입니다.

## 배포와 복구

1. 코드 PR 검토 후 운영 DB 복구 지점/백업을 확보합니다.
2. **운영자의 별도 승인하에** `drizzle/0028_community_safety.sql`만 운영 DB에 적용합니다. 기존 테이블/기록을 수정하는 SQL은 없습니다.
3. 신규 5개 테이블과 기존 게임·계정·재화·꾸미기 수를 확인합니다.
4. 실제 적용한 SQL의 SHA-256을 `deploy-schema.json`에 추가한 뒤 코드 배포합니다. 적용 전에는 배포 검사가 의도적으로 차단됩니다.
5. 가상 이용자로 신고 → 운영 처리 → 안내/이의 → 해제, 회원/게스트 차단, 비밀번호 방 입장을 확인합니다.

문제가 있으면 이전 Worker 버전으로 되돌리고 신규 테이블은 유지합니다. 이전 버전에서는 새 안전 기능이 동작하지 않으므로 외부 공개를 일시 제한할지 운영자가 판단해야 합니다. 이 PR은 운영 DB, 기존 신고 원본, 계정·게임 기록을 변경하지 않습니다.

신고·조치 증거의 자동 삭제는 이번 범위에 없습니다. 개인정보처리방침에 실제 보관 동작과 요청 경로를 추가했습니다. 법적 보존 기간을 임의로 단정하지 않으며, 외부 공개 전 운영자가 보관 정책을 확정해야 합니다.
